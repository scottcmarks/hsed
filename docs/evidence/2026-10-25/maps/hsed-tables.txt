##### hsed-tables

SUMMARY:
hsed embeds Core Spec section 5.1.3 ("Column Types", PDF pages 99-127 of TCG_Storage_Architecture_Core_Spec_v2.01_r1.00.pdf, printed pages 82-110) as 100 `[ttype| ... |]` and 19 `[tenum| ... |]` quasiquote blocks in src/System/SED/MCTP/Common/TypeUIDs.hs, each wrapped in `{- -}` comments carrying the surrounding spec prose (section headings 5.1.3.1 through 5.1.3.100 and the 5.1.1/5.1.2 preamble). A third, bespoke quasiquoter `[t240| ... |]` in TableUIDs.hs embeds Core Spec Table 240 "Table UIDs" (46 rows). All three parse hand-transcribed ASCII-art tables (`+---+---+` separator lines, `|`-delimited cells, multi-line cells concatenated per column) with attoparsec at compile time via `parseTable` (THUtil.hs:47), where any parse failure is a compile error.

What is generated today is thin: `ttype` emits only `u<Name>Type :: UID` (built from `uid b0..b7`) and `f<Name>Type :: String` holding the Format column verbatim with commas and no spaces (e.g. `fAC_elementType = "List_Type,*,ACE_expression"`); the Format string is NOT parsed (TypeUIDs.hs:495 "the Format column is just ignored!", README TODO "Parse Format field of Type Table row tables"; `formatSpecParser` is `undefined` at TypeUIDs/TH.hs:342,345). `tenum` emits `data Core_<name> = Core_<name>_<Label> | ...` deriving (Bounded, Enum, Eq, Ord, Show) with gap-filling `_NA` constructors so that `fromEnum` equals the spec value; it only accepts 2-column tables with `N` or `N-M` value cells, which is why Table 87 gen_status (3 columns, "7 to 31") is left as a commented FIXME. `t240` emits per table row `u<T>TableObject`, `u<T>Table :: UID`, `h<T> :: HalfUID`, and `oth<T>`/`bth<T>` typed half-UIDs, plus two `Map`s to names. Separately, Format.hs defines the binary `Known_Core_Type` GADT (format codes 0-15) with a StreamItem encoder/decoder whose uidref parsers are `undefined`, and Simple_Type.hs hand-duplicates the Simple_Type rows as type synonyms with the comment "All this should be generated by the processing of the Types table".

For the new program this matters in two ways. First, the ASCII grammar is strict and positional (column widths come from the `+` positions in the first separator; every row line must have `|` at exactly those offsets and the same indentation), so a PDF-extraction pipeline would be better off emitting the parsed triple (UID, Name, Format-token list) directly than re-rendering ASCII art for these parsers. Second, the hand transcription contains both deliberate corrections of PDF typos (Fractoin->Fraction, Eror->Error, `_object _ref` -> `_object_ref`, dash-split names) and accidental corruptions (Seconds' UID is all zeros; feedback_size, fraction_enum and gen_status all carry date's UID `00 00 00 05 00 00 18 04`; two caption mis-numberings), so the PDF-anchored source must become authoritative and the hsed file should be regenerated from it, not treated as ground truth.

RISKS:
  - hsed's transcription is not a faithful copy of the PDF: four UIDs are wrong (Seconds all zeros; feedback_size, fraction_enum, gen_status duplicate date's 18 04) and two captions are mis-numbered. Any plan that bootstraps the PDF annotations from the Haskell text would bake these errors in; the direction must be PDF -> code, with hsed regenerated and diffed.
  - The ttype/tenum ASCII grammar is positional and brittle (exact '|' offsets, identical indentation, no blank lines inside, single space between table number and name in tenum captions, exactly 3 or 2 columns). A PDF-extracted table rendered as ASCII would have to reproduce these invariants exactly; it is simpler to bypass the ASCII layer and feed the parsed (UID, Name, [Format tokens]) and [(range, label)] records to the existing Dec generators (dTypeTableRow, dEnum, dUIDRow).
  - The Format column is still an opaque String; nothing in the build currently derives Haskell types, sizes, enum ranges or uidref targets from it. Table 240 names (e.g. 'ACETableUID', 'ColumnTable_UID', 'C_AES_*TableUID') appear only as text inside Format strings and are not resolved to the t240-generated UIDs. The '*' (implementation/SSC-specific) placeholders have no representation.
  - tenum silently merges duplicate labels (padding_type None/None_1) and synthesizes Core_<x>_NA constructors for gaps from 0, including for enums whose spec range starts at 1 (reencrypt_state, reencrypt_request, table_kind, month_enum, day_enum, year_enum 1970-9999 would create ~1970 NA constructors if it ever got a tenum). Deriving Enum from constructor order is the only link between constructor and wire value.
  - Table 87 gen_status (3 columns, 'N to M' ranges, overlapping '34-63' row, spans a page break) and Tables 113/123/124 (values defined elsewhere) are outside the current grammar; the PDF annotation scheme needs a way to express multi-column enum tables, 'to' ranges, and cross-references to tables outside 5.1.3.
  - PDF text extraction of these tables is lossy in ways visible already: cells wrap across lines and across page breaks (Tables 83, 87, 112 are split by footers/headers), the header row repeats after a page break, the PDF itself contains typos (Fractoin, Eror, 'object _ref' with a stray space) and inconsistent spacing ('uidref {X}' vs 'uidref{X}', 'Restricted_Reference_Type {6}'). The annotation layer must carry the corrected canonical tokens rather than rely on re-extracting the glyph text.
  - Spec version drift: hsed transcribes Core Spec 2.01 r1.00; the task names the same PDF, but Opal SSC 2.30 adds/overrides types and table UIDs, and TableUIDs.hs hard-codes which tables are byte tables (only 'MBR'), so the byte/object classification will need to come from the spec data rather than a code constant.
  - TypeUIDs.TH has no tests (THSpec is a single pendingWith); regressions in the generators would only surface as compile failures or silently wrong UIDs.
OPEN QUESTIONS:
  - Should the canonical annotation record for a 5.1.3 table be the already-tokenized triple (UID bytes, Name, [Format tokens]) or the ASCII table text that today's quasiquoters accept? The former avoids the brittle positional grammar; the latter keeps TypeUIDs.hs diffable against the annotations.
  - Were the Seconds / feedback_size / fraction_enum / gen_status UID errors ever noticed downstream (e.g. anything keyed on uSecondsType), or is the generated UID set currently unused at runtime?
  - What should the compiler do with '*' in Format cells (AC_element, ACE_columns, ACL, SSC, type_def, log_row_ref, cred_object_uidref's C_*_ wildcards): a Reader-style implementation parameter as the 2019 comment suggests, or an SSC-overlay value from the Opal PDF?
  - How should enum tables that live outside 5.1.3 (messaging_type -> Table 179, protect_types -> [3], reencrypt_request -> 5.7.2.2.14) and the 3-column Table 87 be anchored and expressed in the annotation grammar?
  - Does the intended pipeline target GHC Template Haskell at all, or will the 'compiler' be a standalone generator that writes ordinary Haskell (or data files) from the annotated PDFs, making the quasiquoters obsolete?
  - Is Core Spec 2.01 r1.00 still the right base, given Opal 2.30 may reference Core 2.01 plus errata/addenda whose type tables differ?

  - Add real hspec coverage for the generators (golden tests on the Dec output for a handful of tables, including Table 105, 149 and 129) before changing them, since THSpec is currently empty.
