##### mh-transport

SUMMARY:
mh_transport (~/mh_transport, GitHub scottcmarks/mh_transport, home-repo submodule pinned at 573fbee, a single commit dated 2026-10-25) is the WebSocket transport factored out of CarolinaCardClub and MHTX. SPEC.md defines protocol v1: one WebSocket per client, every frame a JSON text object with a string "type"; the server sends "hello" (v, server_id, seq, heartbeat intervals, free-form app payload) first, the client sends "ping" every interval_ms and the server answers "pong"; the server drops a client silent for timeout_ms (close 4000); "broadcast" stamps every server→all frame with a running seq so a reconnecting client can judge none/some/unknown missed. Implementations: a pure-Dart client (MhTransportClient, 504 lines) with injected connectors, exponential backoff with equal jitter, an attempt-id race guard and legacy-server tolerance; a Dart hub (MhTransportHub) and a Python hub (TransportHub, starlette/FastAPI). runConformance plus bin/conformance.dart is a language-neutral conformance runner (8 checks, needs only a ws URI and optional HTTP emit/count hooks); both hubs pass it, and the Python one is exercised via conformance_fixture.py under portfolio's venv. There is no Haskell code anywhere in it.

Fit for the SED program: the connection lifecycle is exactly what a host↔simulator LAN link needs and is already debugged (connect/retry/backoff, heartbeat both directions, dead-peer detection, a per-process server_id whose change tells the host "the simulator restarted", in-order delivery over one socket, pluggable connectors incl. self-signed wss). The hub's onMessage/on_message hook hands the application each client frame together with the originating socket, and the client has send(), so a point-to-point request/response can be layered on today purely as application frame types (SPEC explicitly gives the application ownership of every non-reserved type) with no change to SPEC v1. What does not fit: there is no request/response or correlation primitive (client.send is fire-and-forget, messages is a broadcast stream, no ids, no timeouts, no pending-request failure on disconnect); the only server→client path with semantics is broadcast-to-all with seq; and binary frames are not usable — SPEC says they are ignored, the Dart side does ignore them, but the Python hub provably tears down the connection on one (KeyError 'text' in receive_text → "client errored" → client removed; observed as close 1006 against the real uvicorn fixture), and the conformance suite has no binary check.

Minimal backward-compatible extension: define application types such as {"type":"sed.req","id":N,"op":"if_send|if_recv|discovery|reset","payload":"<base64>", plus comID/protocol fields} and {"type":"sed.rsp","id":N,"status":..., "payload":"<base64>"}; the hub replies to the sender's own socket (allowed by SPEC L87-88, which says unicast app frames need not carry seq, and the Dart client already tolerates seq-less frames). Dart hub needs nothing; Python hub needs either an awaitable on_message (today the handler is called synchronously and a coroutine result would be dropped; the same inspect.isawaitable pattern already exists for hello_app) or the app schedules the reply with asyncio.create_task. The Dart client needs a small request() helper (subscribe-before-send, correlate by id, timeout, fail all pending on DisconnectedEvent) which could live in mh_transport or in the SED jig. A v2 with raw binary frames would first require fixing the Python receive loop to ws.receive() with text/bytes dispatch and adding a binary conformance check; base64 at a few KB per IF-SEND/IF-RECV is well within any default WebSocket size limit so v2 is optional. A Haskell client and/or hub would be written from scratch against SPEC.md (no Haskell exists; hsed has no network dependencies at all), but the Dart conformance CLI can certify a Haskell hub without touching any Dart code, which materially lowers the cost. Caveat: python/mh_transport.py is reached by symlink from portfolio/trading_app/backend/, so any change there ships to the live MHTX host on its next deploy.

RISKS:
  - python/mh_transport.py is a symlink target for the live MHTX backend (portfolio/trading_app/backend/mh_transport.py): any change made for the SED program (async on_message, binary receive loop, new frame handling) ships to the production trading host on its next deploy; the conformance suite plus python/test_mh_transport.py are the only regression gate, and the live host must have ~/mh_transport checked out beside portfolio.
  - The Python hub violates SPEC.md L21 today: a single binary WebSocket frame kills the connection (KeyError 'text' in receive_text, observed as close 1006). Any 'v2 binary frames' plan, or any client that accidentally sends binary, hits this first; the conformance suite would not catch it because it has no binary check.
  - No request/response primitive exists: client.send is fire-and-forget, throws StateError when disconnected, has no ids/timeouts, and a reconnect silently loses in-flight requests. A correlation layer must fail pending requests on DisconnectedEvent and decide retransmission policy at the SED layer (IF-RECV re-poll is benign; blind IF-SEND replay is not idempotent at the ComPacket/session level).
  - Python on_message is called synchronously; an async reply handler would be a never-awaited coroutine (silent drop with only a RuntimeWarning). A TPer written on the Python hub must either schedule replies with asyncio.create_task or the hub must be extended to await awaitable handlers.
  - Server-to-client semantics are broadcast-to-all with seq. If more than one host connects to one simulator, unicast replies must go to the originating socket only; using broadcast for replies would leak responses to every connected host and perturb seq-based resync judgments.
  - No Haskell implementation exists and hsed has no network dependencies; both a Haskell client and a Haskell hub would be new code. hsed also pins lts-17.7 while this Mac has only GHC 9.4.7 and no stack snapshots or pantry index, so adding websocket/aeson/base64 dependencies to hsed cannot even be resolved offline here, and the resolver choice may need revisiting before any network code lands.
  - Heartbeat defaults (20 s ping / 60 s dead) and the client's 3 s helloTimeout / 5 s connectTimeout are tuned for app push, not for a test jig; a long-running IF-SEND to a real drive on one side should not be confused with a dead peer, but a synchronous TPer that blocks its event loop while servicing a request would stop answering pings.
  - mh_transport is a one-commit repo (573fbee) extracted the same day as this survey; CCC and MHTX were just cut over to it, so churn here has two live consumers with no slack.
  - Authentication is explicitly not part of the transport; a LAN simulator endpoint reachable from other machines would be unauthenticated unless the SED program adds its own ?token= check as MHTX does.
OPEN QUESTIONS:
  - Which process is the hub (server)? Natural mapping is simulator/TPer = hub, host = client, but the hub exists only in Dart and Python: does the Haskell TPer get its own from-scratch Haskell hub (certifiable with the existing conformance CLI), or does a thin Python/Dart hub process front a Haskell TPer over stdio/pipes?
  - Should the request/response helper (ids, timeouts, fail-on-disconnect) live in mh_transport as a shared, generic layer (benefiting CCC/MHTX later) or stay private to the SED jig so the production-shipped python/mh_transport.py is untouched?
  - Base64-in-JSON application frames (zero transport change) versus a v2 with raw binary frames (requires fixing the Python receive loop, extending Protocol.decode, and adding conformance checks): is the few-KB payload size ever expected to grow past the point where base64 overhead matters?
  - Should the Python hub's binary-frame crash be fixed independently as a SPEC conformance bug (and a binary-frame check added to runConformance), given that fix ships to MHTX?
  - Does a Haskell client need the full SPEC client behaviour (backoff, legacy-server tolerance, resync judgment) or only hello/ping/pong plus request/response, with a reduced client contract documented in SPEC?
  - Can hsed's lts-17.7 resolver be kept if websockets/aeson/base64-bytestring are added, and does the SED program build on this M1 at all given only GHC 9.4.7 is installed (out of scope to install here)?
  - How should the simulator signal a TPer-level reset or power cycle to the host: reuse server_id change (process restart) and/or a broadcast type, versus an explicit reset request/response op?
  - Is per-request ordering sufficient from one WebSocket's in-order delivery, or does the SED layer also need a monotonically increasing request id that the TPer rejects out of order?
RECOMMENDATIONS:
  - Reuse mh_transport for the LAN leg as-is at the connection level (lifecycle, heartbeat, reconnect, server_id/seq restart detection, connectors) and carry SED traffic as application frames, e.g. {"type":"sed.req","id":N,"op":"if_send|if_recv|discovery|reset","proto":..,"comid":..,"payload":"<base64>"} and {"type":"sed.rsp","id":N,"status":..,"payload":"<base64>"}. This needs no SPEC change (SPEC.md L31-33, L87-88) and no change to either consumer.
  - Reply on the originating socket only: in Dart via the onMessage(from, frame) channel (hub.dart L90); in Python by scheduling ws.send_text with asyncio.create_task from the sync on_message, or by extending TransportHub to await awaitable handlers using the inspect.isawaitable pattern already at mh_transport.py L79-81. Keep broadcast for simulator-wide notifications only.
  - Add a small request helper on the client side (subscribe to messages before send, correlate by id, per-request timeout, fail every pending request on DisconnectedEvent/ConnectedEvent with a new server_id). Put it in the SED jig first; promote it into mh_transport only if a second consumer wants it.
  - Treat the Python hub's binary-frame crash as a SPEC bug to fix separately (switch serve() to ws.receive() and dispatch on text/bytes, ignoring bytes), add a 'binary frame is ignored' check to runConformance, and run the full Dart suite plus python/test_mh_transport.py before anything touching python/mh_transport.py is deployed to MHTX.
  - Defer a binary v2: a few KB per IF-SEND/IF-RECV base64-encoded is far below default WebSocket limits; revisit only if payloads grow or latency measurements say the JSON path matters.
  - If a Haskell hub is written, write it against SPEC.md and certify it with `dart run mh_transport:conformance ws://host:port/ws --emit ... --count ...` (bin/conformance.dart), exposing emit/count HTTP hooks the way conformance_fixture.py does; this reuses the existing cross-language gate with no Dart changes.
  - Keep the transport ignorant of SED semantics (matches ARCHITECTURE.md L247-249: vocabularies stay per app). Retransmission, session/ComID state and reset semantics belong in the SED layer above sed.req/sed.rsp.
  - Record the host-side identity/auth decision: if the simulator endpoint is reachable beyond localhost, adopt MHTX's ?token= pre-hello check (SPEC.md L90-95) rather than extending the transport.
