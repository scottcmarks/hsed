##### pdf-structure

SUMMARY:
Both target PDFs are clean, modern, machine-friendly files: PDF 1.5 produced by "Acrobat PDFMaker 11 for Word" / "Adobe PDF Library 11.0", unencrypted with every permission bit set (annotating is allowed), linearized, US-Letter, with a full text layer on every page (Core: 306 pages, 117,609 positioned words; Opal 2.30: 101 pages, 24,098 words), bookmarks with /XYZ destinations (Core 1,369 entries to depth 6; Opal 181), and only /Link annotations today (Core 1,114; Opal 452). Crucially both are fully TAGGED PDFs (MarkInfo /Marked true): the structure tree carries /Table, /TR, /TH, /TD elements (Core 250 top-level tables, 4,584 TD; Opal 63 tables, 5,189 TD) whose leaves are MCIDs that map to marked-content spans in the page content streams. Walking that tree recovered Table 46 AC_element cell-for-cell (UID / Name / Format; 00 00 00 05 00 00 08 01 / AC_element / List_Type, *, ACE_expression) and the Opal Table 20 preconfiguration rows, and it already stitches page-spanning tables (Core: 40 tables span 2-3 pages; Opal: 16 span up to 23 pages). In Core the caption "Table 46 AC_element" is the immediately preceding struct sibling (tagged /L -> /LI, a Word list-style caption); in Opal the caption is the preceding /P. So there are two independent ways to recover tables: geometry (pymupdf page.find_tables) and the tag tree; they agree.

Geometry works but needs care: tables are drawn as filled rectangles ('re'/'f'), and pymupdf's default strategy="lines" over-segments (Table 46 comes out 2x9; Opal Table 20 21x37), while strategy="lines_strict" gives the true grid (Table 46: 2x3; Opal Table 20: 6x15 with the 15 column headers including the rotated "MandatoryWrite Granularity"; Table 21 MethodID 9x4; Tables 30/31/32 on page 51 all correct). Table.extract() text mangles underscores and wrapped words ("AC element _", "Obje ct"); page.get_text("words", clip=cell) returns "AC_element" intact. Opal's /Table /A /BBox attributes are unreliable (16 are full-page, some are garbage like [0,-16382,...]), so the Rect for an anchor should come from word/drawing geometry, not the tag attribute.

The feasibility experiment succeeds on every axis. A /Text annotation with /F 2 (Hidden) anchored to Table 46's bbox on Core page 100 (PDF-space Rect [176.28 259.38 462.72 318.36]) with a 99-byte JSON /Contents payload plus a private /HSED dictionary renders pixel-identically to the original under three independent renderers: Ghostscript 10.08.0 png16m 100 dpi (same md5 22362afc..., 0 differing pixels), MuPDF, and Apple CoreGraphics via sips (what Preview uses); /F 6 (Hidden|Print) is also identical; the same annotation with /F 4 draws a 22x28 px note icon (563 pixels differ) in gs and CoreGraphics. Re-opening with pikepdf and pypdf recovers /Contents (JSON round-trips equal), /F, /Rect and /HSED; pymupdf sees the annot and returns the 15 words inside the Rect, and find_tables(clip=Rect) finds the one table; a pypdf visitor_text pass recovers the same 8 text runs.

Writer choice matters for "the rest of the file byte-for-byte": pikepdf/qpdf has no incremental-update mode, so even a no-change pdf.save() rewrites the file (+39,051 bytes, de-linearized, /ID[1] changed; with the annotation +39,388 bytes, original is not a byte prefix, render identical, outline and tag tree preserved). pymupdf doc.save(incremental=True, encryption=PDF_ENCRYPT_KEEP) appends +1,198 bytes with the original as exact prefix but adds a Popup annot, /NM, /C and an unused appearance XObject. pypdf PdfWriter(path, incremental=True).add_annotation() is the cleanest: +1,010 bytes, original as exact prefix, just the rewritten page dict, the annot and an xref stream. RISKS:
  - pymupdf's default find_tables strategy ('lines') over-segments these Word-generated tables (Table 46 -> 9 columns; Opal Table 20 -> 37 columns, multi-line UID cells split into rows); only 'lines_strict' gives the true grid, and Table.extract() text mangles underscores and wrapped words. A geometry-only extractor built on the defaults would silently produce wrong column counts and corrupted identifiers.
  - The tag tree gives logical cells but no trustworthy geometry: /Table /A /BBox is missing on most Core tables and garbage/full-page on many Opal tables, and pymupdf does not expose MCIDs. Deriving a per-cell Rect requires a custom content-stream pass (track Tm/Td per MCID) or matching MCID text runs to pymupdf rawdict chars.
  - pikepdf (qpdf) cannot write incremental updates: any save rewrites the whole file (+39 KB, de-linearized, /ID[1] changed). If pikepdf is the writer, the 'reads unchanged' guarantee rests on render-equivalence tests, not on byte-prefix preservation.
  - pymupdf's incremental writer adds noise (Popup annot, /NM, /C, appearance XObject, '% Written by MuPDF' comment) and an explicit '/AP null' changes what gs draws; pypdf's incremental writer is clean but emits a spurious '/Flags 0' and does not update /ID[1]. Whichever writer is chosen, outputs should be validated by re-reading with all three libraries and by the gs/sips/MuPDF md5 triple.
  - Multi-page tables: Opal has a table spanning 23 pages and Core has 40 spanning 2-3 pages; per-page geometry yields fragments with repeated header rows that must be stitched, whereas the struct tree already stitches them. Any anchoring scheme must decide whether an annotation anchors a logical table or a page fragment.
  - Hidden annotations are not drawn or printed by gs, MuPDF or CoreGraphics, but behaviour in Acrobat's Comments panel and in other viewers' annotation lists was not tested here; tooling that 'flattens', 'sanitizes' or re-saves the PDF (including Preview's own save) may strip or rewrite them.
  - Anchors are page+Rect+caption; a future TCG revision (new page breaks, renumbered tables) invalidates every Rect, so payloads need enough redundant identity (caption text, header row, content hash) to re-anchor by text search rather than by coordinates.
  - Most fonts are not embedded (Arial, Trebuchet, Courier New, Arial Narrow); glyph widths come from the font dicts so word bboxes are deterministic, but pixel renders differ across machines, so render-md5 comparisons must be done on the same machine/renderer before and after.
  - Opal's docinfo carries Microsoft AIP labels including a 'P2 Confidential' label applied in 2025 on a document also labelled 'External Public'; redistributing annotated copies should keep TCG's license notice and the labels untouched, and the license terms for distributing modified copies were not checked.
  - The venv runs on Homebrew Python 3.15.0 (very new); pip installed pymupdf 1.28.2 rather than the pymupdf-2.0 wheel staged in the scratch dir, so results are tied to MuPDF 1.28.2 behaviour of find_tables.

RECOMMENDATIONS:
  - Treat the tag tree as the primary structural index: caption element (Core /L->/LI, Opal /P) immediately preceding each /Table, then /TR -> /TH|/TD -> MCID -> content-stream text. It is exact, already stitches page-spanning tables, and is independent of rendering. Use geometry (lines_strict, words clipped to cell bboxes) only to compute Rects and as a cross-check.
  - Write annotations as a true incremental update so the original bytes remain an exact prefix (pypdf PdfWriter(path, incremental=True) today; or a tiny custom appender), and keep pikepdf/pymupdf as readers/validators. Add a CI check: original bytes == prefix of annotated file, plus gs/MuPDF/CoreGraphics page-render md5 equality.
  - Use /F 6 (Hidden|Print) rather than /F 2 alone so the annotation is suppressed on both screen and print paths, keep /Contents as human-readable JSON for debuggability, and put the structured payload in a private dictionary (/HSED) plus a document-level manifest listing every anchor with a version number and a hash of the anchored words.
  - Make each payload self-re-anchoring: include caption text, header row, struct-tree path (e.g. Document/Sect/Table index), page label and a hash of the words inside the Rect, so a future spec revision can be re-matched by text rather than by coordinates.
  - Build a small MCID-geometry pass (pikepdf parse_content_stream tracking Tm/Td/TJ per MCID, or match MCID text runs to pymupdf rawdict chars) so cell Rects can be derived for the tag-tree cells; do not use /Table /A /BBox.
  - Run the Python extractor with `python -I` on any PDF that did not come from the repo, and keep all experiments on copies in the scratch dir; the originals in ~/hsed/tcg were not touched (md5 5ceb93ab118a578125e3755eb885b668 for Core).
