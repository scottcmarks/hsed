##### spec-tables

SUMMARY:
The two PDFs contain 298 numbered tables in total: 248 in the Core Spec 2.01 body (the List of Tables prints only 247; Table 185 "C_AES_128/C_AES_256 ResidualData Column Values After..." exists in the body at PDF p176 but is omitted from the LoT) and 50 in Opal SSC 2.30. Every numbered table was verified to have a unique body caption line of the form "Table N  Title" (Core) or "Table N - Title" (Opal), which makes the caption a reliable anchor string for a PDF annotation. Page mapping is PDF = printed + 17 for Core and PDF = printed + 1 for Opal. By class, Core is 235 (A) directly compilable, 6 (B) needs interpretation, 7 (C) prose; Opal is 48 (A), 1 (B), 1 (C). The large A population is dominated by Core 5.1.3 column types (Tables 46-165, 120 tables), the Base/Admin/Clock/Crypto/Locking/Log "Table Description" schema tables (169-178, 180-208, 211-215, 218, 220-223, 225-229, 233-234), the Appendix UID assignments (237-248), the Section 3 token/packet/ComID/Level-0 byte layouts (4-44), and all 31 Opal preconfiguration tables (18-29, 33-48).

hsed already embeds, by table number, 137 of the 248 Core tables as spec-text comments consumed by Template Haskell quasiquoters: Tables 4-16 (Token.hs), 46-165 (TypeUIDs.hs, via tenum/ttype), 171 (Table.hs), 239 and 241 (SpecialPurposeUIDs.hs), and 240 (TableUIDs.hs plus a bespoke quasiquoter in TableUIDs/TH.hs that parses the literal title "Table 240   Table UIDs"). Two captions in TypeUIDs.hs are mis-numbered relative to the published PDF (uinteger_4 labelled "Table 147", uinteger_8 labelled "Table 160"; the PDF has 157 and 161). The 111 Core tables not covered by number include the whole packet/ComID/Level-0 layer (17-45), status codes (166), Properties (167-168), every Table Description except 171, all preconfiguration/default-authority tables (209, 216), and UID tables 242-248. No Opal 2.30 table is embedded anywhere in hsed/src.

Opal 2.30 behaves as an overlay on Core: Section 3.1.1 (Tables 2-12) instantiates Core Tables 39/42/43/44 bit layouts and then pins each field to a constant or VU in a bulleted "SHALL return" list; Tables 14-17 narrow Core 26 (ComIDs), 4 (tokens), 127/128 (reset_types) and 167/168 (Properties minima); Section 4 preconfiguration tables supply concrete rows (UIDs, names, ACLs, PINs) for the Core Table Description schemas of the Admin SP (18-29) and Locking SP (34-48); Tables 30-33 add a new type, enum, table description and preconfig (DataRemovalMechanism); Table 49 replaces Core 102/103 (life_cycle_state enum, adding manufactured states 8-13) and Table 50 adds two columns to Core 171 (Table table). Beyond numbered tables, both specs carry class-B unnumbered code-shaped content: ~51 unique Core method signatures (`X.Method[ Name : type, Name = type ] => [ ... ]`, 53 "=>" lines) plus 18 abstract types in 5.1.4 with "Format:" pseudo-code, and 3 Opal signatures (Activate, Revert, RevertSP).

The chief bearing on the program: Core's horizontal tables and the hsed-embedded sections extract cleanly with gs txtwrite, but every Opal preconfiguration table (31 tables, including the 22-page Locking SP AccessControl Table 38 and 7-page Admin SP AccessControl Table 22) uses rotated column headers and some rotated cell text that txtwrite reduces to letter fragments, and the Opal legend (Table 1) assigns normative-adjacent meaning (fixed vs. personalizable access control, VU values, (N) columns) to cell shading and bold-underline font that no text extraction preserves. Both PDFs are tagged (StructTreeRoot/MarkInfo), have outlines, use object streams, and already carry /Annots arrays, so a structure-aware PDF library rather than txtwrite is needed for the Opal compiler input and for safe annotation insertion.
