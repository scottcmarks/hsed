##### tcg-protocol

SUMMARY:
The host-to-TPer contract is a three-level stack. At the bottom, Core 2.01 §3.3 (printed p.36-49; PDF page = printed + 17) abstracts every interface as two commands, IF-SEND and IF-RECV, each carrying a command block {Protocol ID 0x01..0x06, Transfer Length (>= 2 bytes, width per interface), ComID} and a data payload. Protocol 0x01 carries ComPackets (Level 0 Discovery on ComID 0x0001, control/regular sessions on any active ComID); protocol 0x02 carries the raw-byte ComID management commands GET_COMID, HANDLE_COMID_REQUEST (VERIFY_COMID_VALID request code 1, STACK_RESET code 2) and GET_COMID_RESPONSE; protocol 0x00 is SPC's security-protocol inventory and is not defined in Core. SIIS 1.20 (PDF page = printed + 1) maps those two commands onto SCSI SECURITY PROTOCOL OUT/IN (ComID in SECURITY PROTOCOL SPECIFIC, INC_512=1 so lengths are in 512-byte units), ATA TRUSTED SEND/RECEIVE [DMA] (SP SPECIFIC=ComID, 512-byte units), and NVMe Security Send/Receive (SPSP0=ComID low byte, SPSP1=ComID high byte, length in bytes, NSID unused). Five interface status codes (Invalid Security Protocol ID, Invalid Transfer Length on IF-SEND, Other Invalid Command Parameter, Synchronous Protocol Violation, Data Protection Error) are returned out-of-band of the payload via sense/ATA status/NVMe SC, so any serialized host<->simulator record must carry an interface status field as well as payload bytes. SIIS has no USB clause: UAS and USB-BOT appear only as reset-mapping tables under the SCSI clause, so a USB adapter path is SCSI SPIN/SPOUT or SAT pass-through of the ATA commands.

The middle level is the ComPacket (20-byte header: Reserved 4, ComID 2, ComID Extension 2, OutstandingData 4, MinTransfer 4, Length 4), containing Packets (24-byte header: Session = TSN(4)|HSN(4), SeqNumber 4, Reserved 2, AckType 2, Acknowledgement 4, Length 4), containing Subpackets (12-byte header: Reserved 6, Kind 2 (0x0000 data, 0x8001 credit), Length 4, then payload padded with zeros to a 4-byte boundary). Exactly one ComPacket per interface command; all integers big-endian. The payload is a TLV token stream (Table 04): tiny 0x00-0x7F, short 0x80-0xBF (1-byte header, 0-15 data bytes), medium 0xC0-0xDF (2-byte header, <=2047), long 0xE0-0xE3 (4-byte header, <=16M-1), F0/F1 Start/End List, F2/F3 Start/End Name, F8 Call, F9 EndOfData, FA EndOfSession, FB/FC Start/End Transaction, FF Empty. A method is Call, InvokingID (8-byte bytes atom), MethodID (8-byte bytes atom), SL, required params, optional params as Named values keyed 0x00.. in signature order, EL, EOD, SL status 0 0 EL; the response is SL results EL EOD SL status 0 0 EL. Session Manager methods use InvokingID SMUID 00..00FF with method UIDs 00..00FF01-06 (Properties, StartSession, SyncSession, StartTrustedSession, SyncTrustedSession, CloseSession), travel in packets with Session=0, and their responses are themselves formatted as method calls. The synchronous protocol (mandatory for the Opal family; Properties Asynchronous=False) runs a per-ComID state machine S1 Awaiting IF-SEND -> S2 Processing -> S3 Awaiting IF-RECV, with Table 45 fixing the (Length, OutstandingData, MinTransfer) triple the TPer returns in each state, a second IF-SEND in S2/S3 rejected with Synchronous Protocol Violation, and methods forbidden from spanning ComPackets.

The top level is the SP table model. A simulator needs, per TPer: ComID state (Inactive/Issued/Associated plus 16-bit extension), per-ComID host Properties (defaults Table 168: MaxComPacketSize 1024, MaxPacketSize 1004, MaxIndTokenSize 968, MaxSubpackets/MaxPackets/MaxMethods 1, all booleans False), the sync state and response buffer, and the control session; per regular session: SP, Write flag, authenticated-authority set, Authenticate challenge state, transaction stack. For the tier-1 host flow (Level 0 Discovery, Properties, StartSession to Admin SP as Anybody, Get MSID, CloseSession) the simulator must implement the Level 0 header plus TPer (0x0001) and Locking (0x0002) feature descriptors (both mandatory) plus the SSC and SIIS (0x0005) descriptors; Properties; StartSession/SyncSession with HostSigningAuthority omitted or Anybody (HostChallenge ignored); Get (MethodID 00 00 00 06 00 00 00 16) with a cell_block whose startColumn/endColumn select the PIN column (column 3) of a C_PIN object, returning RowValues [3 = bytes]; and EOS handling. Tables: Admin SP's SP table (Admin SP row UID 00 00 02 05 00 00 00 01), SPInfo, TPerInfo, Authority (Anybody 00 00 00 09 00 00 00 01, SID ..06, Admins ..02), C_PIN (SID row 00 00 00 0B 00 00 00 01; the MSID row is Opal-defined), MethodID, AccessControl rows keyed (InvokingID, MethodID) with an ACL of ACE uidrefs whose BooleanExpr is a postfix expression over Authority uidrefs; absence of a row or unsatisfied ACL yields NOT_AUTHORIZED (0x01). Tier 2 adds Authenticate (..1C, ThisSP, Proof=password, result Success boolean, wrong password gives SUCCESS status with False), Set (..17) with Values = RowValues (named 1) on C_PIN SID, Opal's Activate/Revert/RevertSP/Erase (UIDs sit in Core's "Reserved for SSC usage" MethodID slots), and the Locking template: LockingInfo, Locking (Global Range 00 00 08 02 00 00 00 01; columns 3 RangeStart, 4 RangeLength, 5/6 Read/WriteLockEnabled, 7/8 Read/WriteLocked, 9 LockOnReset, 0xA ActiveKey), K_AES_128/256 with GenKey (..10), MBRControl (00 00 08 03 00 00 00 01: Enable, Done, MBRDoneOnReset default Power Cycle) and the MBR byte table read/written with Get/Set using Row-addressed cell_blocks and Bytes values. Reset events (Power Cycle, Hardware Reset) are first-class inputs to the simulator because SIIS maps transport events onto them and they drive ComID expiry, session abort, Properties reset, LockOnReset and MBRDoneOnReset.

FACTS:
  1. Core abstracts every interface command as IF-SEND or IF-RECV with a command block of {Protocol ID 0x01..0x06, Transfer Length (at least 2 bytes; width varies by interface), ComID (for protocols 0x01, 0x02, 0x06)} plus a data payload.
     [Core 2.01 Table 24, printed p.36 (PDF p.53), /private/tmp/claude-501/-Users-scott-hsed/f05c341b-63d7-4ac7-8e79-f36321a58c77/scratchpad/bytecontract/core/p053.txt]
  2. Protocol IDs: 0x00 = see SPC [6]; 0x01 and 0x02 defined in Core; 0x03-0x06 'Reserved for TCG' in Core 2.01 (SIIS 1.20 later uses 0x06 for SCSI byte-count mode and 0x03 for NVMe). IF-SEND/IF-RECV to an unsupported protocol in 0x00-0x06 fails with interface status 'Invalid Security Protocol ID Parameter'.
     [Core Table 25 and text, printed p.36-37 (PDF p.53-54); SIIS Tables 12-13, 23-24, printed p.29-30, 51-52]
  3. All commands mapping to IF-SEND/IF-RECV with protocol ID in {0x01..0x06} SHALL be routed to the TPer; TPer-layer and communication-layer commands use Protocol ID 0x02; management-layer (control session) and session-layer traffic use Protocol ID 0x01.
     [Core §3.3.4.2-3.3.4.6, printed p.43-45 (PDF p.60-62)]
  4. ComID assignments: 0x0000 reserved; 0x0001 Level 0 Device Discovery; 0x0002-0x07FF reserved for TCG; 0x0800-0x0FFF vendor unique; 0x1000-0xFFFF dynamically managed 'non-reserved' ComIDs. Support for dynamic ComID management is SSC-specific.
     [Core Table 26, printed p.38-39 (PDF p.55-56)]
  5. A ComID is in one of three states: Inactive, Issued (returned by GET_COMID, no session yet), Associated (one or more open sessions). Issued->Inactive on hardware reset/power cycle or MaxComIDTime expiry; Associated->Inactive on reset/power cycle or when all sessions close and no startup is in progress; TPer may inactivate any ComID at any time; ComIDs are issued sequentially and never reissued while active.
     [Core §3.3.3 and Figure 4, printed p.39-40 (PDF p.56-57)]
  6. Extended ComID is 4 bytes: ComID (2, MSB first) then a 2-byte ComID Extension generated by the TPer at each issuance; extension is 0x0000 for reserved (0-4095) and statically assigned ComIDs; extension 0xFFFF is reserved to signal that the host used an inactive ComID; Extended ComID states are Inactive/Issued/Associated/Invalid.
     [Core §3.3.3.1, printed p.40 (PDF p.57)]
  7. IF-SEND to an Inactive non-reserved ComID: a dynamic-ComID TPer accepts and silently discards the whole payload with good status; a non-dynamic TPer may instead report 'Other Invalid Command Parameter'. IF-SEND/IF-RECV to an unsupported reserved ComID: 'Other Invalid Command Parameter'.
     [Core §3.3.3.2-3.3.3.3, printed p.41-42 (PDF p.58-59)]
  8. IF-RECV to an Inactive non-reserved ComID returns a header-only ComPacket with ExtendedComID = {ComID from CDB, 0xFFFF}, OutstandingData 0, MinTransfer 0, Length 0 and good status.
     [Core §3.3.3.3, printed p.41 (PDF p.58)]
  9. GET_COMID = IF-RECV, Protocol ID 0x02, Transfer Length 0x0001 (interface units), ComID 0x0000; payload bytes 0-3 = allocated Extended ComID, all zeros if none can be assigned; TPer never assigns extension 0xFFFF.
     [Core Tables 27-28, printed p.43-44 (PDF p.60-61)]
  10. HANDLE_COMID_REQUEST = IF-SEND, Protocol 0x02, Transfer Length 0x0001, ComID = allocated ComID; payload = 4-byte Extended ComID + 4-byte Request Code (+ request-specific fields). GET_COMID_RESPONSE = IF-RECV, Protocol 0x02, same ComID; bytes 10-11 of the response carry the available data length; TPer zero-pads short responses and truncates long ones to the transfer length. Requests and responses are expected in pairs; a later request replaces the pending response.
     [Core §3.3.4.7, Tables 29-30, printed p.45-46 (PDF p.62-63)]
  11. 'No Response Available' payload: bytes 0-3 Extended ComID (zeros if no request preceded), 4-7 Request Code 0x00000000, 8-9 reserved, 10-11 length 0x0000, rest reserved zeros.
     [Core Table 31, printed p.46 (PDF p.63)]
  12. VERIFY_COMID_VALID: request code 0x00000001. Response: bytes 0-3 Extended ComID, 4-7 0x00000001, 8-9 reserved, 10-11 0x0022 (available length), 12-15 state (0 Invalid, 1 Inactive, 2 Issued, 3 Associated), 16-25 allocation time, 26-35 expiry time, 36-45 time since reset, each a 10-byte {Year u2, Month u1, Day u1, Hour u1, Minute u1, Second u1, Fraction u2, Reserved u1}; all-zero times if no RTC.
     [Core Tables 32-34, printed p.46-48 (PDF p.63-65)]
  13. STACK_RESET: request code 0x00000002; fewer than 8 payload bytes -> 'Invalid Transfer Length parameter on IF-SEND'. Effect for that ComID: abort all sessions (no CloseSession prepared), abort uncommitted transactions and pending session startups, invalidate all command/response buffers, abort method processing, reset the protocol stack to initial state, reset Properties/ComID properties to defaults, no notification. Response bytes 10-11 = 0x0004, 12-15 = 0x00000000 success / 0x00000001 failure; 'Pending' response has length 0x0000. Response cleared by full retrieval, hard reset/power cycle, or another HANDLE_COMID_REQUEST.
     [Core §3.3.4.7.5, Tables 35-37, printed p.48-49 (PDF p.65-66)]
  14. Level 0 Discovery: IF-SEND Protocol 0x01 ComID 0x0001 is undefined; TPer transfers, discards the data and returns good status. IF-RECV Protocol 0x01 ComID 0x0001 may be issued at any time without sessions; response truncated to Transfer Length if shorter, padded per the interface spec if longer; data is NOT packetized.
     [Core §3.3.6.1-3.3.6.2, printed p.50 (PDF p.67)]
  15. Level 0 Discovery header (48 bytes): bytes 0-3 Length of Parameter Data (total valid bytes of header + descriptors, excluding this field), 4-5 Data Structure Major Version = 0x0000, 6-7 Minor Version = 0x0001, 8-15 reserved, 16-47 vendor unique; feature descriptors follow from byte 48 in increasing feature-code order, only for implemented features.
     [Core Tables 38-39, §3.3.6.2.1-3.3.6.3, printed p.50-51 (PDF p.67-68)]
  16. Feature codes: 0x0001 TPer, 0x0002 Locking, 0x0003-0x00FF reserved, 0x0100-0x03FF SSCs, 0x0400-0xBFFF reserved, 0xC000-0xFFFF vendor unique. Descriptor template: bytes 0-1 Feature Code, byte 2 bits 7-4 Version / bits 3-0 reserved, byte 3 Length (multiple of 4), bytes 4-n feature data.
     [Core Tables 40-41, printed p.52 (PDF p.69)]
  17. TPer feature descriptor (mandatory): code 0x0001, version 0x1, length 0x0C; byte 4 bit0 SyncSupported, bit1 AsyncSupported, bit2 ACK/NAK Supported, bit3 BufferMgmt Supported, bit4 Streaming Supported, bit5 reserved, bit6 ComID Mgmt Supported, bit7 reserved; bytes 5-15 reserved.
     [Core Table 42, §3.3.6.4, printed p.52-53 (PDF p.69-70); bit order inferred from column layout in txtwrite output, needs visual check]
  18. Locking feature descriptor (mandatory): code 0x0002, version 0x1, length 0x0C; byte 4 bit0 LockingSupported, bit1 LockingEnabled (a Locking-template SP exists in any state other than nonexistent), bit2 Locked (any range with ReadLockEnabled&ReadLocked or WriteLockEnabled&WriteLocked), bit3 MediaEncryption, bit4 MBREnabled (MBRControl.Enable true), bit5 MBRDone (MBRControl.Done true), bits 6-7 reserved.
     [Core Table 43, §3.3.6.5, printed p.53-54 (PDF p.70-71)]
  19. SIIS feature descriptor: code 0x0005, Data Structure Version 0x1, length 0x0C, byte 4 SIIS Revision Number (0x20 = SIIS v1.20), byte 5 bit0 Key Change Zone Behavior, bits 2:1 Identifier Usage Scope (00b not indicated, 01b NSID/LUN not used for PR impact, 10b used), bytes 6-15 reserved.      [SIIS Tables 2-4, printed p.20-22 (PDF p.21-23)]
  20. SIIS adds method status codes INCOMPATIBLE_MBR_FORMAT = 0x13 and WP_DATA_REMAIN = 0x14 to the Core status code table.
     [SIIS Table 1, printed p.20 (PDF p.21)]
  21. ComPacket header (20 bytes, big-endian): bytes 0-3 Reserved, 4-5 ComID, 6-7 ComID Extension, 8-11 OutstandingData, 12-15 MinTransfer, 16-19 Length (payload bytes), payload from byte 20. One ComPacket per interface command; a ComPacket never spans commands; packets never span ComPackets; subpackets never span packets; tokens MAY span subpackets and packets.
     [Core §3.2.3.1, Table 17, printed p.23 (PDF p.40); endianness §3.2.2.2 printed p.15]
  22. OutstandingData (TPer->host): total bytes still available on this ComID excluding the current ComPacket but including ComPacket/Packet/Subpacket overhead; 0 if nothing more, 0xFFFFFFFF if more than that, 0x00000001 if still processing and nothing ready. MinTransfer (TPer->host): minimum bytes the host must request to get the next packet, including overhead, 0 if none. Both are reserved (0) host->TPer.
     [Core §3.2.3.2.1.4-3.2.3.2.1.5, printed p.24 (PDF p.41)]
  23. Packet header (24 bytes): bytes 0-7 Session (0-3 TSN, 4-7 HSN), 8-11 SeqNumber, 12-13 Reserved, 14-15 AckType (0x0000 none, 0x0001 ACK, 0x0002 NAK), 16-19 Acknowledgement, 20-23 Length, payload from byte 24.
     [Core Table 18, §3.2.3.3.1, printed p.24-26 (PDF p.41-43)]
  24. Subpacket kinds: Data 0x0000, Credit Control 0x8001. Data subpacket header (12 bytes): bytes 0-5 Reserved, 6-7 Kind, 8-11 Length (data bytes, excluding pad); payload is the token stream followed by (-Length mod 4) zero pad bytes. Credit Control subpacket: Length always 0x00000004, bytes 12-15 Credit.
     [Core Tables 19-21, printed p.26-28 (PDF p.43-45)]
  25. B=0 integer (S=sign), B=1 bytes (S=continued; BS=11 non-final segment, 10 final). Zero-length bytes = 0xA0. Integers SHOULD use the shortest atom. Empty atom may appear anywhere and is ignored.

RISKS:
  - Bit-field tables (Core Tables 42/43 feature-descriptor bits, Table 04 token bit patterns, SIIS Table 2 byte 5) come out of gs txtwrite as scrambled column text; I inferred bit positions from column order (bit0 = Sync/LockingSupported ... bit6 = ComID Mgmt, bit5 = MBRDone). A compiler that extracts 'anchored spec text' from the PDF will hit the same problem, so annotations must state bit positions explicitly rather than rely on extracted table text; verify these few tables visually before coding.
  - Version skew: Core 2.01 (2015) lists protocols 0x03-0x06 as reserved and calls the out-of-band errors 'TPer errors', while SIIS 1.20 (2025) defines 0x06 (SCSI byte-count) and 0x03 (NVMe), renames them 'TPer Interface Status Codes', adds status codes 0x13/0x14 and the SIIS feature 0x0005, and references an 'upcoming new Core spec'. Annotating Core 2.01 as the single source will silently omit these.
  - Interface status is out-of-band: five error outcomes (Invalid Security Protocol ID, Invalid Transfer Length on IF-SEND, Other Invalid Command Parameter, Synchronous Protocol Violation, Data Protection Error) are reported as SCSI sense / ATA status 0x51 error 0x04 / NVMe SC, never inside the payload. A serialized command/response stream that carries only payload bytes cannot express them; on the raw ATA register path (no SDR) all five collapse to one value, so a real-drive test cannot distinguish them while a simulator can.
  - Transfer-length units differ per transport (SCSI and ATA: non-zero multiples of 512 bytes with INC_512 = 1; NVMe: bytes; protocol 0x02 requests use 'Transfer Length 0x0001' which is 512 bytes on SCSI/ATA). The host jig must pad ComPackets to 512-byte multiples on SCSI/ATA, and the simulator must tolerate trailing pad beyond ComPacket.Length and zero-pad short responses.
  - The synchronous protocol is stateful per ComID and interface-ordering dependent (one IF-SEND or IF-RECV in flight per ComID; a second IF-SEND is a protocol violation). Over mh_transport (WebSocket, possibly multiplexed) the host side must serialize per ComID exactly as a SCSI host would, otherwise the simulator will legitimately report Synchronous Protocol Violation.
  - Reset semantics are transport events, not payload: Power Cycle and Hardware Reset inactivate ComIDs, abort sessions, reset Properties, set LockOnReset locks and clear MBRControl.Done. Without an explicit reset message in the serialized protocol the simulator can never be driven through these paths, and tier-2 (locking ranges, MBR) test coverage would be incomplete.
  - Opal-specific identifiers are not in Core or SIIS: MSID C_PIN row, Locking SP UID, Admin1/User1 authorities, LockingRange1.., the Opal feature descriptor (0x0203) with its static base ComID, Activate/Revert/RevertSP/Erase method UIDs, and Opal's raised Properties minimums. Core only shows the 'Reserved for SSC usage' MethodID slots (06..0011, 06..0202, 06..0203, 06..0803). These must come from the Opal 2.30 reader; my recollection (C_PIN_MSID 00 00 00 0B 00 00 84 02, Locking SP 00 00 02 05 00 01 00 02, Activate 06..0203, Revert 06..0202, RevertSP 06..0011, Erase 06..0803) is unverified here.
  - Core permits tokens to span subpackets and packets and permits continued (multi-atom) byte values; even though Opal's synchronous profile forbids methods spanning ComPackets, a codec that assumes one method per subpacket or no continued tokens will reject some legal streams.
  - ACL evaluation is a postfix boolean expression over Authority uidrefs stored as alternative-typed list elements (ACE_expression); encoding it in the simulator's tables requires the Type-table machinery that Scott's errata notes say is still being reworked in hsed.
